## What is AGE?
**AGE (Actually Good Encryption)** is a tool which allows to Encrypt and Decrypt files easily. What makes special AGE is the impossibility of making errors, because it doesn't give the power to the user to change some configurations (reducing the user's surface of action).

AGE not only gives the opportunity to do **Symmetric Encryption** but also a **Public-Key Encryption**. More in details, for Public-Key Encryption, in reality it is used an **Hybrid Encryption** approach (it will be discussed later) to guarantee Confidentiality, Integrity, Authenticity and also Confidentiality for the Symmetric Key thanks to the usage of an **Elliptic Curve Diffie-Hellman Key Exchange**.

## Examples of AGE's usage

### Symmetric Encryption
It is possible to encrypt with a Symmetric key with the following command:

```bash
$ age -p secret.txt > secret.txt.age
```
Thanks to the `-p` flag, it is asked to the user to insert a password (if the user choose not to, `age` will create it automatically). To decrypt: 
```bash 
 $ age -d secrets.txt.age > secrets.txt
```
It will be asked to put the password decided before.

#### More details
As we can imagine, this implementation is based on a concatenation of algorithms: `scrypt(KDF)` and `chacha20-poly1305`, in particular, the choice to chain `scrypt` and `ChaCha20-Poly1305` addresses specific engineering constraints:

1. **Mitigation of Weak Passwords via `scrypt`:** Since users often choose low-entropy passphrases, `age` utilizes `scrypt` for key derivation. Its memory-hard design forces a high hardware cost for parallelized brute-force attacks (e.g., via ASICs/FPGAs), providing a stronger security margin than CPU-bound KDFs like PBKDF2.
    
2. **High-Performance, Safe Encryption via `ChaCha20-Poly1305`:** Unlike AES, which relies on specific hardware instructions (AES-NI) to avoid cache-timing side-channel attacks, ChaCha20 provides secure, constant-time execution in pure software. Combined with Poly1305 for integrity, it offers a robust and portable primitive suitable for diverse hardware environments.

### Public-Key Encryption

To use asymmetric encryption, users must first generate a key pair (an **Identity/Private key** and a **Recipient/Public key**). Encryption is performed using the public key (Recipient), and decryption requires the private key file (Identity). This is an example of usage the Public-Key Encryption for **Confidentiality** .

First, generate an identity file with the command `age-keygen`:

```
$ age-keygen -o key.txt
Public key: age1ql3z7hjy54pw3hyww5ayyfg7zqgvc7w3j2elw8zmrj2kg5sfn9aqmcac8p
```
In key.txt is present the **Identity**.

Then, encrypt a file using the public key via the `-r` (recipient) flag:

```bash
$ age -r age1ql3z7hjy54pw3hyww5ayyfg7zqgvc7w3j2elw8zmrj2kg5sfn9aqmcac8p secret.txt > secret.age
```

To decrypt, the `-i` (identity) flag is used to specify the file containing the private key:

```bash
$ age -d -i key.txt secret.age > secret.txt
```

#### Example of usage

```
$ age-keygen -o key.txt
Public key: age1ql3z7hjy54pw3hyww5ayyfg7zqgvc7w3j2elw8zmrj2kg5sfn9aqmcac8p

$ echo "This is a message for the key holder" > message.txt

$ age -r age1ql3z7hjy54pw3hyww5ayyfg7zqgvc7w3j2elw8zmrj2kg5sfn9aqmcac8p message.txt > message.age

$ cat message.age
age-encryption.org/v1
-> X25519 zK2AY53nYxvXqnbU3J7dw...
(binary ciphertext data)

$ age -d -i key.txt message.age > message_decrypted.txt

$ cat message_decrypted.txt
This is a message for the key holder
```

#### More details

In this mode, `age` implements a modern **Hybrid Encryption** (or Envelope Encryption) scheme. The architecture abstracts the complexity of session management from the user:

1. **Key Exchange via `X25519`:** Unlike older tools relying on RSA, `age` uses **X25519** (Curve25519 Diffie-Hellman) for the asymmetric layer. This ensures shorter keys (making them easier to handle and copy-paste) and faster computation times while maintaining a high security level comparable to much larger RSA keys.
    
2. **The "Envelope" Architecture:** When encrypting to a public key, `age` automatically generates a random ephemeral symmetric key (the "file key"). This file key encrypts the actual data using **ChaCha20-Poly1305**. The file key is then encrypted (wrapped) using the recipient's public key and stored in the file header. This combines the convenience of asymmetric cryptography with the performance of symmetric encryption.
    
3. **Sender Anonymity (No Signing):** It is important to note that `age` focuses on confidentiality and data integrity, but explicitly omits digital signatures. Since anyone with the public key can encrypt a file, `age` guarantees that only the holder of the private key can read it, but it does not cryptographically prove _who_ sent it (Sender Anonymity).

## Comparison with Legacy Tools (OpenSSL)

While tools like OpenSSL are ubiquitous in engineering environments, `age` represents a paradigm shift in how file encryption is approached. The comparison highlights the trade-off between **flexibility** (OpenSSL) and **safety-by-design** (`age`).

#### 1. Cryptographic Agility vs. Opinionated Security

**OpenSSL** acts as a "Swiss Army Knife": it exposes virtually every cryptographic primitive available (AES-128, AES-256, RC4, DES, etc.) and every mode of operation (ECB, CBC, CFB, GCM).

- **The Risk:** This puts the burden of choice on the user. An engineer might accidentally choose a weak algorithm (e.g., `aes-128-ecb`) or misuse parameters (e.g., reusing an IV), leading to insecure deployments.
    

**`age`** follows an **"Opinionated Design"**:

- **The Solution:** It features **no configuration options** regarding algorithms. It removes "cryptographic agility" intentionally. The user cannot choose a weak cipher because `age` only implements the current best practice (X25519 + ChaCha20-Poly1305).
    

#### 2. The Danger of Unauthenticated Encryption

A critical distinction lies in data integrity.

- **OpenSSL (`enc` command):** Historically, the default file encryption with OpenSSL uses **AES-CBC** (Cipher Block Chaining). While confidentiality is preserved, CBC does not guarantee integrity. This makes files vulnerable to **Padding Oracle Attacks** and bit-flipping, where an attacker can modify the ciphertext without the decryption failing, potentially corrupting data or leaking information.
    
- **`age`:** By strictly enforcing **AEAD (Authenticated Encryption with Associated Data)** via ChaCha20-Poly1305, `age` ensures that any tampering with the encrypted file results in an immediate decryption failure. If the file is modified, `age` refuses to output any data.
